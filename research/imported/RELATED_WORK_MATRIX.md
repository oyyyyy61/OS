# Related-Work Mechanism Matrix

Last audited: 2026-07-23

This document freezes the M0 related-work boundary for the proposed multi-Agent
DAG KV-cache lifecycle system. The comparison is mechanism-level: inputs,
prediction model, cache object, actions, constraints, sharing semantics, and
objective are compared separately. Similar terminology alone is not treated as
evidence of novelty.

## Decision

**Pause the original C1 and C2 claims before implementation.** PBKV already
aggregates predicted future access value from multiple active workflows at a
shared physical radix-cache node and uses that value for lifecycle decisions.
PBKV, KVFlow, TokenCake, Continuum, and Hermes collectively cover most of the
original C2 signal combination: history, workflow future, fanout or branch
information, memory cost, eviction, retention, and proactive loading. AgentKV
also occupies the explicit semantic identity, invalidation, and fail-closed
lifecycle contract space; those properties are treated as required substrate.

Work may resume only with the narrower boundaries below:

- **Revised C1:** dependency-correct probabilistic lease aggregation for a
  shared physical block, including first versus repeated reuse, mutually
  exclusive and correlated branches, independent workflows, fanout
  deduplication, probability calibration or robust bounds, and explicit
  reference/lifetime invariants.
- **Revised C2:** a constrained joint controller whose GPU-capacity and DMA
  shadow prices are derived from a stated primal/dual problem and updated
  online, with resource feasibility, stability, update overhead, and joint
  retain/migrate/release/prefetch actions demonstrated. A weighted heuristic
  labeled as a shadow price does not meet this boundary.
- **Revised C3:** deadline-aware proactive transfer at block/chunk granularity
  with partial-prefix matching, one physical transfer shared by compatible
  waiters, cancellation and failure propagation, deadline urgency, long-job
  blocking control, and fairness. Each element must be evaluated against
  KVFlow, PBKV, Hermes, Strata, and the local exact-signature implementation.

## Overlap Scale

| Label | Meaning |
|---|---|
| Critical | The central claimed mechanism and target object are already present. Renaming or small policy changes cannot sustain the claim. |
| High | Most mechanism dimensions are present; a precise additional invariant, optimization formulation, or protocol is required. |
| Medium | Important inputs or actions overlap, while the target object or decision scope differs. |
| Low | Primarily infrastructure, objective, or workload adjacency. |

## Artifact and Trace Implications

The closest public evaluations do not establish one trace format containing all
of DAG topology, physical prefix/block identity, reuse distance, calibrated
branch probability, fanout, deadline, arrival time, token counts, transfer
events, and execution result:

- PBKV evaluates HoVer/LangChain, SWE-bench/AutoGen, and
  FinanceBench/CrewAI-style dynamic workflows, but its paper-level workload
  description does not establish the full proposed event/accounting contract.
- KVFlow uses controlled synthetic workflows and a PEER-style Financial QA
  simulation; this is insufficient as evidence for a real trace distribution.
- Hermes builds a ten-application workload suite and profiles each application
  into PDGraph JSON, while its evaluation samples arrival timing from Mooncake.
  The published schema is a demand profile, not a physical block lifecycle log.
- Mooncake publishes production-style request/prefix characteristics, while
  Agent-DAG branch and deadline fields are outside its trace model.
- [KVCache Cache in the Wild (USENIX ATC 2025)](https://www.usenix.org/conference/atc25/presentation/wang-jiahao)
  establishes that reuse time and probability vary globally and become more
  predictable by request category. Its public paper does not establish the
  complete joint Agent-DAG field set required here.

Accordingly, C4 should initially be framed as a reproducible benchmark and
trace artifact. It may become a dataset contribution only after a documented
field-by-field audit shows that public artifacts cannot supply the joint fields,
and after licensing, anonymization, collection protocol, leakage-resistant
workflow/template/time splits, and a data card are complete.

## M0 Gate

The original C1/C2 wording remains **paused**. M2/M3 implementation may proceed
only after `RESEARCH_CONTRACT` and `CLAIM_EVIDENCE_LEDGER` adopt the revised
boundaries above, name PBKV and KVFlow as first-order baselines, name the local
vLLM feature accurately, and preregister mechanism metrics that can distinguish
the proposed controller from existing scores and heuristics.
